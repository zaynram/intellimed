# Trust Generator v2.2 Design Specification

**Date:** 2026-03-31
**Branch:** `zaynram/issue2`
**Status:** Design approved, pending implementation plan

---

## 1. Overview

v2.2 polishes the v2.1 release with three goals:

1. **Gender-inclusive party labels** — Replace hardcoded "Husband"/"Wife" with configurable labels
2. **Bug fixes and dead code cleanup** — Address 12 code review findings
3. **UX overhaul** — Make the GUI intuitive for non-technical legal personnel (paralegals)

### Scope Boundaries

**In scope:** Schema refactor, generator restructuring, GUI UX improvements including list editing, draft management, tooltips, elections grouping, validation UX, documentation alignment.

**Out of scope (v2.3):** Firm config GUI settings screen, SSN masking/encryption, import format documentation, python-docx type stubs, generic docx row parser extraction.

**Risk note:** This is a large release combining a cross-cutting schema rename with major GUI additions. The implementation is sequenced as 11 steps, each producing a green test suite. The schema rename (step 3) is the highest-risk change and is delivered as a single atomic commit to avoid broken intermediate states. If time pressure requires descoping, the GUI UX polish items (step 8: tooltips, elections grouping, validation indicators) are the first candidates for deferral — they are additive and do not affect correctness.

## 2. Party Label Refactor

### 2.1 Schema Field Rename

Rename `husband` / `wife` fields on `TrustData` to `party_a` / `party_b`:

```python
class TrustData(BaseModel):
    model_config = ConfigDict(populate_by_name=True)

    party_a: PersonInfo = Field(default_factory=PersonInfo, validation_alias="husband")
    party_b: PersonInfo = Field(default_factory=PersonInfo, validation_alias="wife")

    party_a_label: str = "Husband"
    party_b_label: str = "Wife"
```

- `validation_alias` accepts old JSON keys (`"husband"`, `"wife"`) during Pydantic model construction and JSON deserialization
- `populate_by_name=True` also accepts new keys (`"party_a"`, `"party_b"`) during construction
- **Important:** `validation_alias` does NOT affect runtime attribute access. After construction, the Python attribute is `party_a` / `party_b`. All `attrgetter()` calls, dotted field path strings (e.g., `"husband.full_legal_name"`), `getattr()` calls, and `_SCALAR_MODELS` keys must be updated to use the new names. This is a codebase-wide find-and-replace of every `"husband"` and `"wife"` in field path strings across: `schema.py`, `validate.py`, `gui.py`, `forms.py`, `cli.py`, `pdf_questionnaire.py`, and all tests.
- Serialization outputs the Python field name (`party_a` / `party_b`)
- `party_a_label` / `party_b_label` control all display text in documents, GUI, questionnaires, and validators
- For `TrustType.INDIVIDUAL`, labels are unused — the document uses "Grantor" throughout

### 2.2 InitialTrustee Enum Rename

Rename member names but preserve serialized values for backward compatibility:

```python
class InitialTrustee(str, Enum):
    BOTH = "both"
    PARTY_A = "husband"   # value stays "husband" for backward compat
    PARTY_B = "wife"      # value stays "wife" for backward compat
```

Comment documents the value-preservation decision.

### 2.3 SsnOwner Enum (replaces free-text field)

Replace `TrustIdentity.whose_ssn_for_tax_id: str` with a proper enum:

```python
class SsnOwner(str, Enum):
    PARTY_A = "party_a"
    PARTY_B = "party_b"
    GRANTOR = "grantor"

class TrustIdentity(BaseModel):
    whose_ssn_for_tax_id: SsnOwner = SsnOwner.PARTY_A
```

Add a Pydantic field validator that coerces old string values: `"wife"` -> `PARTY_B`, `"husband"` -> `PARTY_A`, `"grantor"` -> `GRANTOR`.

The `ssn_owner_name` computed property becomes a clean match on the enum instead of string matching.

### 2.4 Computed Property Renames

| Old | New |
|-----|-----|
| `husband_name` | `party_a_name` |
| `wife_name` | `party_b_name` |

Both use `get_or_default` consistently (fixes finding #3 — the old `wife_name` asymmetry).

### 2.5 Label Propagation

Every hardcoded "Husband"/"Wife" string becomes dynamic via `data.party_a_label` / `data.party_b_label`:

| Location | Example Change |
|----------|---------------|
| Trust document text | `f'{name_a} is "{label_a}" and {name_b} is "{label_b}"'` |
| Schedule C/D headings | `f"{label_a}'s Separate Property"` |
| Printable questionnaire sections | `f"{label_a} Information"` |
| Printable elections | `f"{label_a} only"`, `f"{label_a} and {label_b} as Co-Trustees"` |
| GUI tabs | `label_a` / `label_b` (dynamic) |
| Validator messages | `f"{label_a}'s Full Legal Name"` |
| PDF field sections | `f"{label_a} Information"` |

### 2.6 GUI Label Presets

The data entry step offers a dropdown for common label combinations:

- Husband / Wife (default)
- Wife / Wife
- Husband / Husband
- Spouse 1 / Spouse 2
- Partner 1 / Partner 2
- Custom... (freeform text fields appear)

### 2.7 Parser Backward Compatibility

The docx parser's section header map and `_CHECKBOX_MAP` are **extended**, not replaced. Both old entries (`"husband information"` -> `party_a`) and new entries (`"party a information"` -> `party_a`) coexist. A test verifies old-format questionnaire parsing.

### 2.8 Printable Questionnaire Round-Trip Safety

The printable questionnaire always emits **canonical checkbox text** internally (e.g., `"Husband only"`, `"Wife only"`) regardless of the party labels used for section headings. This ensures the docx parser can always match `_CHECKBOX_MAP` entries when a printed questionnaire is filled out and re-imported. A note in the elections section explains: "For parser compatibility, election options use standard legal terminology." This avoids the combinatorial explosion of trying to match arbitrary custom label strings in the parser.

### 2.9 Individual Trust Behavior

For `TrustType.INDIVIDUAL`:
- `party_a_label` / `party_b_label` are ignored; all document text uses "Grantor"
- `InitialTrustee` dropdown is hidden in GUI (grantor is always the trustee)
- Spousal elections (surviving amendment, property classification) are hidden or set to N/A
- Printable questionnaire shows "Grantor as sole Initial Trustee" (no dropdown)

## 3. Bug Fixes

### 3.1 GUI Assign Lambda Overwrites User Data (Critical #1)

**Problem:** `stub_placeholder()` calls in `_add_review_sections()` use `assign=lambda` callbacks that fire eagerly during list construction, unconditionally overwriting `state_of_governing_law` and `county_of_execution`.

**Fix:** Replace with a **pre-review defaulting step**. After parsing or data entry, before displaying the review screen, apply config defaults to empty jurisdiction fields once. The review step becomes read-only — it never mutates TrustData.

```python
def _apply_jurisdiction_defaults(self):
    """Apply config defaults to empty jurisdiction fields before review."""
    if not self.data.trust_id.state_of_governing_law:
        self.data.trust_id.state_of_governing_law = self.config.jurisdiction.default_state
    if not self.data.trust_id.county_of_execution:
        self.data.trust_id.county_of_execution = self.config.jurisdiction.default_county
    if not self.data.trust_id.date:
        self.data.trust_id.date = datetime.now().strftime("%B %d, %Y")
```

Called once before entering Step 2 Review, preserving user-provided values.

### 3.2 Placeholder Strings Leak Into Documents (Critical #2)

**Problem:** `get_or_default` returns `<field.path>` when no default is provided. These leak into generated legal documents.

**Fix:** Two changes:
1. `get_or_default` returns `"[MISSING]"` instead of `<field.path>` — visible to reviewers, not mistakable for real data, greppable.
2. Add `_pre_generation_check()` on `_TrustDocGen` that blocks generation if any critical field is `"[MISSING]"` or empty.

**Critical fields (exhaustive list):**
- `trust_name`, `trust_date`, `state`, `county`
- `grantor_name` (individual) OR `party_a_name` + `party_b_name` (joint)
- `trustee_names`, `ssn_owner_name`

The `--force` flag bypasses this check.

### 3.3 `party_b_name` Asymmetry (Important #3)

Resolved by the rename — both `party_a_name` and `party_b_name` use `get_or_default` consistently.

### 3.4 Docx Parser Auto-Detection Brittleness (Important #4)

**Fix:** Emit `log.warning()` when the XOR heuristic activates:

```
"Auto-detected trust type as INDIVIDUAL because only one grantor name was provided.
If this is a joint trust, ensure both names are filled in the questionnaire."
```

### 3.5 CLI Crashes If Reportlab Missing (Important #5)

**Fix:**
1. Move `generate_fillable_pdf` import from top of `cli.py` into the `create-fillable-pdf` subcommand handler (lazy import).
2. Fix `generators/__init__.py` to conditionally add to `__all__`:

```python
__all__ = ["generate_printable_questionnaire", "generate_trust_document"]
try:
    from .pdf_questionnaire import generate_fillable_pdf
    __all__.append("generate_fillable_pdf")
except ImportError:
    pass
```

### 3.6 No Mutual Exclusivity Validation (Important #6)

**Fix:** Add validator warnings:
- `INDIVIDUAL` trust with populated `party_a` or `party_b` -> WARNING
- `JOINT` trust with populated `grantor` -> WARNING

### 3.7 PDF Questionnaire Scalar-Only (Minor #7)

**Fix:** Document the limitation in CLI help text:

```
"Generates a fillable PDF covering grantor/party information and trust identity.
For complete intake including children, assets, and beneficiaries, use the .docx questionnaire."
```

### 3.8 InitialTrustee Inappropriate for Individual (Minor #8)

Resolved by section 2.8 — hide the dropdown for individual trusts.

### 3.9 Printable Questionnaire Elections Ignore trust_type (Minor #9)

**Fix:** Pass `trust_type`, `party_a_label`, and `party_b_label` to the elections section. Branch:
- Individual: "Grantor as sole Initial Trustee" (no dropdown options)
- Joint: `f"{label_a} and {label_b} as Co-Trustees"`, `f"{label_a} only"`, `f"{label_b} only"`

Hide irrelevant spousal elections for individual trusts.

### 3.10 `MISSING_COMPUTED` Dead Code (Minor #10)

Remove the unused `FieldStatus.MISSING_COMPUTED` variant.

### 3.11 Version Unification (Minor #11)

- Set `pyproject.toml` version to `2.2.0`
- Set `pixi.toml` version to `2.2.0`
- Remove hardcoded `__version__ = "2.0.0-alpha"` from `trust_document.py`
- Add `importlib.metadata.version("trust-generator")` in `__init__.py` to expose `__version__`

### 3.12 `create-fillable-pdf` Lacks `--individual` Flag (Minor #12)

**Fix:** Add `--individual` flag mirroring `create-printable`. Pass `trust_type` to `generate_fillable_pdf()`. When individual, omit Party A/B sections and show only Grantor section.

## 4. Generator Refactoring

### 4.1 Article Split (Articles 3, 4, 5)

Articles 3, 4, and 5 are *entirely different legal documents* per trust type — not parameterizable variants. Extract into separate methods:

- `_article_3()` dispatches to `_article_3_individual()` / `_article_3_joint()`
- `_article_4()` dispatches to `_article_4_individual()` / `_article_4_joint()`
- `_article_5()` dispatches to `_article_5_individual()` / `_article_5_joint()`

### 4.2 Pronoun Substitution Map

For the ~40% of `if self.is_individual` blocks that are pure pronoun/label swaps, use a `_phrasing` cached property:

```python
@cached_property
def _phrasing(self) -> dict[str, str]:
    if self.is_individual:
        return {
            "subject": "I", "object": "me", "possessive": "my",
            "reflexive": "myself", "subject_verb": "I have",
            "trustee_ref": "the Trustee", "grantor_ref": "the Grantor",
        }
    return {
        "subject": "We", "object": "us", "possessive": "our",
        "reflexive": "ourselves", "subject_verb": "We have",
        "trustee_ref": "our Trustee", "grantor_ref": "the Grantors",
    }
```

Each of the 39 `if self.is_individual` blocks is categorized during implementation as:
- **Pronoun swap** -> use `_phrasing` dict
- **Structural difference** -> separate method (Articles 3/4/5)
- **Minor divergence** -> inline if/else (kept as-is)

### 4.3 Party Label Properties on `_TrustDocGen`

Add convenience properties for document text:

```python
@property
def label_a(self) -> str:
    return self.d.party_a_label

@property
def label_b(self) -> str:
    return self.d.party_b_label

@property
def party_a(self) -> str:
    return self.d.party_a_name

@property
def party_b(self) -> str:
    return self.d.party_b_name
```

### 4.4 Pre-Generation Check

```python
def _pre_generation_check(self) -> None:
    """Block generation if critical fields are missing."""
    critical = {
        "trust_name": self.trust_name,
        "trust_date": self.trust_date,
        "state": self.state,
        "county": self.county,
        "trustee_names": self.trustee_names,
        "ssn_owner_name": self.d.ssn_owner_name,
    }
    if self.is_individual:
        critical["grantor_name"] = self.grantor_name
    else:
        critical["party_a_name"] = self.party_a
        critical["party_b_name"] = self.party_b

    missing = [k for k, v in critical.items() if not v or v == "[MISSING]"]
    if missing:
        raise ValueError(
            f"Cannot generate: missing critical fields: {', '.join(missing)}. "
            f"Run validation first or provide the required data."
        )
```

Called at the top of `build()`. Bypassed by `--force`.

### 4.5 Refactor Sequencing

Two commits for safety:
1. **Commit 1:** Pure structural split + pronoun map. No label changes. Verify document output is identical to pre-refactor.
2. **Commit 2:** Party label dynamism. All hardcoded "Husband"/"Wife" strings replaced.

## 5. Draft Management

### 5.1 Storage

```
%APPDATA%/trust-generator/drafts/
├── 2026-03-31_anderson_family.json
├── 2026-03-28_martinez.json
└── ...
```

- Files named `{YYYY-MM-DD}_{slug}.json` where slug is derived from trust name or grantor last name (lowercased, spaces replaced with underscores, non-alphanumeric stripped)
- Content is `TrustData.model_dump_json(indent=2)` with **SSN fields excluded** from serialization (`exclude={"party_a": {"ssn"}, "party_b": {"ssn"}, "grantor": {"ssn"}}`). SSNs must be re-entered or re-imported when resuming a draft. This avoids persisting client PII in plaintext files on paralegal workstations.
- Auto-purge: drafts older than 90 days are deleted on application startup (configurable via `config/firm.toml` under `[drafts]` section)
- Overwrite if same slug+date exists; otherwise create new
- Directory created on first save

### 5.2 New Module: `drafts.py`

~80-100 lines. Functions:

- `drafts_dir() -> Path` — returns `%APPDATA%/trust-generator/drafts/`, creates if needed
- `save_draft(data: TrustData) -> Path` — serialize and save, return path
- `list_drafts() -> list[DraftInfo]` — scan directory, return sorted by most recent
- `load_draft(path: Path) -> TrustData` — deserialize
- `delete_draft(path: Path) -> None` — remove file
- `draft_display_name(data: TrustData) -> str` — trust name if available, else grantor last name + " Trust", else "(Unnamed Trust)"

`DraftInfo` is a simple dataclass: `path`, `display_name`, `modified_date`.

### 5.3 GUI Flow Changes

**Step 0 (Mode Selection)** gains a third option:

```
How would you like to begin?

  [Import Questionnaire]    [New Trust]    [Continue Draft]

Import: Parse a completed .docx or .pdf questionnaire
New Trust: Enter client data directly
Continue Draft: Resume a previously saved trust
```

**Draft Picker** (when "Continue Draft" selected):

- Listbox showing drafts: `"Anderson Family Trust — Mar 31, 2026"`
- Sorted most recent first
- "Open" loads into data entry step
- "Delete" removes with confirmation dialog
- "Back" returns to mode selection
- If no drafts exist, show `"No saved drafts found."` with a Back button

**Save in data entry step:**

- "Save Draft" button (relabeled from current) triggers `save_draft()`
- Shows brief confirmation: `"Draft saved."`
- No file picker — fully managed

**"Continue in Data Entry" button on review step:**

- Shown when imported data has validation errors
- Loads parsed TrustData into the data entry form
- Auto-saves as draft when entering data entry mode this way
- Enables the paralegal to fix gaps in the GUI instead of re-editing the source document

### 5.4 Removal of File Picker Dialogs

The current "Save Draft" / "Load Draft" buttons use `filedialog.asksaveasfilename` / `filedialog.askopenfilename`. These are replaced entirely by the managed draft system. No raw file dialogs for drafts.

## 6. UX Improvements

### 6.1 List Editing (Critical Gap)

Add `ListEditor` widget to `forms.py`. Used for all list-type fields in the data entry step.

**Widget behavior:**
- Displays items as rows, each with inline text fields matching the item's schema
- "Add" button appends a blank row at the bottom
- Each row has a "x" (remove) button; non-empty rows prompt confirmation
- Minimum 0 rows (all lists are optional)
- Tab order flows through fields within a row, then to next row

**New data entry tabs:**

| Tab | List Fields |
|-----|------------|
| Family | Children (name, DOB, relationship, minor checkbox) |
| Trustees | Successor Trustees (order, name, relationship, contact) |
| Beneficiaries | Beneficiary Shares (name, relationship, share %, conditions), Specific Bequests (item, recipient), Withdrawal Schedule (step, timing, percentage) |
| Assets | Sub-tabs: Real Property, Financial Accounts, Vehicles, Insurance, Pensions, Valuables — each with fields matching the schema model |

**Data binding:** `ListEditor.get_items() -> list[dict]` and `ListEditor.set_items(items: list[dict])` for serialization to/from TrustData.

### 6.2 Human-Readable Election Labels

Replace raw enum values in dropdowns with descriptive labels:

| Field | Old Values | New Display Labels |

| `initial_trustee` | "both", "husband", "wife" | "Both Grantors as Co-Trustees", "{label_a} only", "{label_b} only" |
| `distribution_standard` | "hems", "broad" | "Health, Education, Maintenance, Support (HEMS)", "Broad Discretion" |
| `beneficiary_death` | "per_stirpes_beneficiary", etc. | "To beneficiary's descendants (per stirpes)", "To grantors' descendants (per stirpes)", "Redistribute among remaining beneficiaries" |
| `remote_contingent` | "intestacy", "charity" | "Distribute per state intestacy laws", "Donate to charity" |

### 6.3 Elections Grouping

Group the 15+ election fields into sub-sections within the Elections tab:

**Trustee Settings:**
- Initial Trustee, Trustee Compensation, Trustee Bond

**Distribution Rules:**
- Distribution Standard, Tangible Distribution, Division Method, Beneficiary Death, Remote Contingent (+ charity name)

**Surviving Spouse:**
- Surviving Amendment Rights, Power of Appointment
- (Hidden for individual trusts)

**Tax & Legal:**
- Property Classification, Retirement Strategy, Insurance Strategy, Portability
- (Property Classification hidden for individual trusts)

**Protections:**
- No-Contest Clause, Spendthrift Protection, Probate Coordination

Each sub-section has a header label. One-line descriptions appear below each field in gray italic text.

### 6.4 Tooltips

Every field label gets a tooltip (hover text) explaining the field in plain English. Examples:

- **Spendthrift Protection:** "Prevents creditors from accessing trust assets. Recommended for most trusts."
- **HEMS:** "Limits distributions to Health, Education, Maintenance, and Support — the standard protective approach."
- **Portability:** "Allows the surviving spouse to use the deceased spouse's unused federal estate tax exemption."
- **No-Contest Clause:** "Discourages beneficiaries from challenging the trust by reducing or eliminating their share if they do."

Implementation: `ToolTip` class that shows a small popup on mouse hover over the label widget.

### 6.5 Field Validation During Entry

Add real-time validation in the data entry step:

- Required fields have a red asterisk (*) after the label
- When a required field loses focus and is empty, show a red border and inline message: `"Required"`
- Tab headers show a status indicator: green checkmark when all required fields are filled, red dot when errors exist
- Validation runs on focus-out events, not on every keystroke (avoids distraction)

Required fields per trust type (for data entry validation — distinct from section 3.2's pre-generation critical fields which also include computed properties like `trust_name`):
- Individual: `grantor.full_legal_name`
- Joint: `party_a.full_legal_name`, `party_b.full_legal_name`
- Both: `trust_id.state_of_governing_law`, `trust_id.county_of_execution`

### 6.6 User-Friendly Error Messages

Wrap all exception displays with human-readable messages. Map common errors:

| Exception Pattern | User Message |
|------------------|-------------|
| `ValidationError` from Pydantic | "Some fields have invalid values. Please check the highlighted fields." |
| `FileNotFoundError` | "The selected file could not be found. Please check the path and try again." |
| `ValueError` from parser | "The questionnaire file appears to be in an unexpected format. Please ensure it is a Trust Intake Questionnaire." |
| `PermissionError` | "Cannot write to the output location. Please choose a different folder or check file permissions." |
| Other exceptions | "An unexpected error occurred. Details: {brief message}" |

Raw stack traces are never shown. A "Show Details" expandable section is available for technical users.

### 6.7 Step-Level Guidance

Each step shows a brief description at the top:

- **Step 0:** "Choose how to start: import an existing questionnaire, begin a new trust, or continue a saved draft."
- **Step 1a (Data Entry):** "Enter the client's information below. Required fields are marked with *. Use the tabs to navigate between sections."
- **Step 1b (Import):** "Select a completed questionnaire file to import. Supported formats: .docx, .pdf"
- **Step 2 (Review):** "Review the information below. Fields marked with [!] have errors that must be fixed. Fields marked with [?] have warnings to review."
- **Step 4 (Results):** "The trust document has been generated. Sections highlighted in red and yellow in the document require attorney review before the trust is finalized."

### 6.8 Trust Type Switching

Allow changing trust type in the data entry step via the Trust Info tab dropdown. When changed:
- Show a confirmation dialog: "Switching trust type will clear [Party A/Party B | Grantor] data. Continue?"
- If confirmed, clear the data in the now-irrelevant fields (prevents conflict with mutual exclusivity validation in section 3.6)
- Show/hide relevant tabs (Party A/B vs Grantor) dynamically
- Show/hide spousal election options

### 6.9 Output Path Selection

Before generation, show the output path and offer a "Change..." button:

```
Output will be saved to:
  C:\Users\...\Anderson_Family_TRUST_20260331.docx    [Change...]
```

### 6.10 "(computed)" Label Replacement

Replace `"(computed)"` with contextual text:
- For state/county: show the actual default value with note, e.g., `"Illinois (default)"`
- For trust name: `"Anderson Family Trust (derived from grantor name)"`
- For trust date: `"March 31, 2026 (today's date)"`
